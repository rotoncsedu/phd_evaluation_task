## Background

Manufacturers want to deliver orders on time. Finishing late harms customers, and finishing early creates storage costs and rework risk. Factories therefore **predict** the throughput time of each order and then **optimize** a schedule around those predictions (*predict-then-optimize*).

In customized production, future orders differ from historical ones, so the feature distribution shifts (a **covariate shift**). Models trained on historical data then predict worse, and worse predictions produce worse schedules.

The paper studies this with data from Aker Solutions, a Norwegian engineering company that produces pipe spools for oil platforms:

| | Setting A (historical, labeled) | Setting B (forthcoming, unlabeled) |
|---|---|---|
| Production orders | 5,830 | 3,866 |
| Period | Jan to Sep 2019 | Sep 2019 to Apr 2020 |
| Features per order | 20 | 20 |
| Throughput labels known when predicting B | Yes | No |

For data privacy, the experiments are **semi-synthetic**. Features are sampled from Gaussian distributions built from the real data's means and covariances, and throughput times are generated by a random forest fitted to real data plus noise. The shift between A and B is controlled by a parameter **θ** (θ = 1, 2, 3, 4), where a larger θ means a stronger shift.

## Method in brief

Three prediction models are compared:

| Model | Description |
|---|---|
| **Elastic Net** | Regularized linear regression |
| **Neural network** | Small baseline network (feature extractor + regressor), trained on setting A only |
| **WDGRL** | The same network trained with Wasserstein distance-guided representation learning. A critic estimates the distance between the latent representations of A and B, and the feature extractor learns to reduce it using only the *features* of B (no labels) |

Predicted throughput times are then fed to an integer linear program (solved with GLPK through PuLP) that schedules the 100 orders with the earliest due dates under a capacity constraint. The **scheduling cost** (early and late penalties) is evaluated with the *actual* throughput times. An **Oracle** that uses the true noise-free outcomes serves as a lower-bound benchmark.

**Tested on:** Windows, Lenovo IdeaPad Pro 5 16IRH8 (CPU only). Python version: `[add your Python version]`.

   ```bash
   git clone https://github.com/rotoncsedu/phd_evaluation_task.git
   cd phd_evaluation_task
   ```
2. Create and activate a virtual environment **outside the repository folder** (or make sure it is listed in `.gitignore`):
   ```bash

   ```
3. Install the dependencies. The code imports:
   `numpy`, `pandas`, `scikit-learn`, `tensorflow` (TensorFlow 2.x with the Keras API; the scripts call `disable_eager_execution()`), `lightgbm`, `joblib`, and `pulp`.
   ```bash
   pip install numpy pandas scikit-learn tensorflow lightgbm joblib pulp
   ```

   ```bash
   pip freeze > requirements.txt
   ```

## How to reproduce the results

Run all commands from the repository root, because the scripts use relative paths such as `data/...` and `results_pred/...`.

**Step 1 (optional): hyperparameter search.** The tuned hyperparameters are already provided in `data/`, so this step can be skipped.
```bash
python cross_validation.py
```

**Step 2: generate data, train models, and predict.**
```bash
python prediction.py
```
For each of 10 random seeds (runs 1 to 10) and each θ in {1, 2, 3, 4}, the script samples the data, trains Elastic Net, the baseline neural network, and WDGRL, and saves the predictions as `theta_<θ>_run_<run>_rf_gaussian_pred_results.npz` (40 files in total). The script writes these files to the current folder, so **move them into `results_pred/`** before the next step.

**Step 3: solve the scheduling problem.**

Open `scheduling.py` and edit the GLPK path in the `prob.solve(...)` call, which currently points to a Windows location on the author's machine. Set it to your own `glpsol` executable, or use `pulp.apis.GLPK_CMD(msg=0)` if `glpsol` is on your `PATH`.
```bash
python scheduling.py
```
The script reads from `results_pred/` and writes one CSV per (θ, run) with the MAE and scheduling cost of the Oracle, Elastic Net, neural network, and WDGRL, named like `theta_<θ>_run_<run>_rf_gaussian_capacity_<K>_cost-ratio_<r>_final_results.csv`. **Move these CSVs into `results_final/`.**

**Step 4: aggregate and visualize.** Average the CSVs over the 10 runs for each θ to obtain the tables in the report. `tables_plots.ipynb` is the notebook I used for the summary tables and plots.

## Experiment settings

The main experiment and the robustness checks differ only in a few variables at the top of the scripts. Change them and rerun the relevant steps:

| Setting | Variable (file) | Main experiment | Alternative |
|---|---|---|---|
| Production capacity | `capacity` (`scheduling.py`) | `70` | `50` (lower capacity) |
| Tardiness cost ratio | `ratio` (`scheduling.py`) | `1` (equal costs) | `2` (tardiness twice as costly) |
| Noise distribution | `error` (`prediction.py`, `scheduling.py`) | `'gaussian'` | `'uniform'` |
| Outcome-generating function | `nonlin` (`prediction.py`, `scheduling.py`) | `'rf'` (random forest) | `'gbm'` (gradient boosting; needs `data/lgb_model.txt`) |

Check the values in your local copy of `scheduling.py` before running. The output file names include the capacity and cost ratio, so results from different settings do not overwrite each other.

## Key results

Mean over 10 runs. **Lower is better** for both metrics. Full tables, figures, and discussion are in [`Report.pdf`](Report.pdf).

**Scheduling cost at the strongest shift (θ = 4):**

| Method | Paper | My replication |
|---|---|---|
| Elastic Net | 4,453.9 | 4,205 |
| Neural network | 4,568.4 | 4,259 |
| **WDGRL** | **2,954.2** | **2,668** |
| Oracle | 600.2 | 575 |

**Prediction error (MAE) in my replication:**

| Method | θ = 1 | θ = 2 | θ = 3 | θ = 4 |
|---|---|---|---|---|
| Elastic Net | 23.5 | 26.6 | 27.0 | 29.6 |
| Neural network | 22.6 | 25.5 | 25.5 | 28.4 |
| **WDGRL** | 23.2 | 23.9 | 23.9 | 22.6 |

**Findings**

- The baselines deteriorate steadily as the shift grows, whereas WDGRL stays stable. At θ = 4, WDGRL reduces the scheduling cost relative to the neural network by 35.3% in the paper and 37.4% in my replication.
- My replication reproduces the ranking of the methods and the qualitative pattern at every θ, but the exact numbers differ moderately from the published ones. Likely causes are random sampling, stochastic neural network training, and software versions.
- At mild shift (θ = 1) the advantage of WDGRL is small or absent, so it pays off mainly for moderate and large shifts.

## Limitations

- Results come from a single replication, so small differences should not be over-interpreted.
- The experiments are semi-synthetic (real feature statistics, simulated throughput times), which is not a pure field test.
- The method addresses covariate shift only, and scheduling is limited to 100 orders on a single capacity-constrained line.

See Section 9 of the report for the full discussion.
